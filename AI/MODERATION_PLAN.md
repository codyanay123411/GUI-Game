## 1. Report window, submission and staff log

Register literal `/report` through the existing Kohl addon command integration, including its slash-command dispatch rather than assuming the semicolon parser handles it. Ordinary players may open a separate Kohl-themed report window outside the dashboard; opening it grants no staff-menu access. List current players by username/UserId, allow one target and a reason, and provide Submit/Cancel plus pending/success/failure. Opening or cancelling writes nothing; pending disables duplicate Submit.

Proposed independent Settings permissions: submit reports = everyone by default; read reports/directory = existing trusted mod/moderator and above; issue warnings = existing admin and above. Resolve configured role names through server Kohl Auth, never client ranks/attributes. Settings edits retain existing Kohl settings-management authorization. Do not reuse creator-only CanConfigureGame or expand GameTester. Recheck read/write authorization after yielding; revoked staff lose live subscriptions/UI data. A permission to submit never grants permission to read.

A small server moderation-state owner validates caller identity from the connection, a real current target UserId (reject self-report by proposed default), trimmed valid UTF-8 reason of 10–500 characters and at most 2,000 bytes, and bounded request identifiers. Resolve usernames server-side. Recheck the selected player after asynchronous validation; a departed target produces readable failure. Proposed limits: one accepted report per 60 seconds and five per ten minutes per reporter, plus a bounded request-rate gate for invalid calls. Keep these configurable. Repeated retries use the same request token, bound to caller and payload; a conflicting payload is rejected. Reports remain allegations and never become warnings automatically.

Canonical server envelope: schemaVersion, eventId, kind, UTC createdAt, reporter {UserId, usernameAtEvent}, target {UserId, usernameAtEvent}, submittedReason, PlaceId, actual JobId. Warning envelopes additionally contain issuing staff identity. UTC time/IDs/context are server-generated; usernames are historical labels and UserId is identity. Studio records absent JobId explicitly, never a fake routable value. No private/reserved access codes, private IDs, webhook secrets or client-supplied server context. Keep this schema reusable server-side for a separately authorized future Discord adapter.

Use experience-scoped DataStores, independent of match/reset/disconnect state. Suggested report canonical key: reporter UserId plus a bounded time bucket; UpdateAsync atomically appends accepted records with rate-limit/dedup receipts. Enforce record-size limits and bounded retries/budgets. Callbacks must be deterministic/non-yielding; generate IDs/filter before the callback and never notify inside it. Record acknowledgement requires durable acceptance or confirmed existing identical receipt. An ambiguous storage failure shows 'Could not confirm save; retry', reusing the token, never false success. Secondary chronological log indices/outbox delivery are retryable and reconciled from canonical records; no multi-key atomicity is claimed. Keep a saved-but-indexing-pending state visible to staff rather than silently losing records.

Filter submitted reasons server-side with TextService before displaying them; staff-only text still needs filtering. Store author UserId with the server-only submitted text and safe filtered fallback, and filter retrieved reasons for the viewing context. On filter failure, withhold the reason with readable feedback; never send raw text to clients. Avoid raw reasons in Output or notification payloads. Raw-text retention/access duration needs a decision below. [Roblox filtering requirements](https://create.roblox.com/docs/ui/text-filtering).

## 2. Staff notifications and ID copy

Publish only after durable acceptance: version, eventId and canonical lookup reference on an experience-scoped MessagingService topic. Each server validates the envelope, deduplicates event IDs, checks each recipient's current permission and loads the authorized filtered record. Notify currently online authorized staff across servers; persistent staff log remains available with nobody online. Bounded publish retry and staff-open/join reconciliation compensate for best-effort delivery; do not promise every live toast arrives. [MessagingService delivery](https://create.roblox.com/docs/reference/engine/classes/MessagingService).

Clicking a report toast/log opens the existing staff detail/log workflow with an explicitly labeled JobId copy field and separate PlaceId. Extend existing Kohl Servers rows, including Current server, with the actual full JobId for authorized staff, preserving discovery, deduplication, Join/Already here and admission/credentials. Do not create another browser. Studio shows 'Current Studio session — JobId unavailable' with no copy/join destination; never copy a PlaceId or local sentinel as JobId.

Supported fallback: clicking JobId/UserId opens or focuses a selectable TextBox with the exact value selected and instructions 'Press Ctrl+C to copy' (platform-appropriate manual instructions elsewhere). Roblox documents TextBox copy/paste and CursorPosition/SelectionStart, not a general experience-script clipboard writer. No `setclipboard`, exploit API or unsupported one-click success claim. Prevent edits from changing the canonical ID and keep map input blocked only by actionable controls. No existing project clipboard helper was found in the scoped adapters; native Kohl behavior still needs inspection. [TextBox support](https://create.roblox.com/docs/reference/engine/classes/TextBox).

## 3. Persistent Players directory and warning history

Mount a staff-only **Players** tab alongside **Members** using the guarded Kohl dashboard addon pattern. Members keeps staff-membership management. Directory contains every real account observed joining after deployment, including offline players; do not claim retroactive knowledge of all historical players. Server PlayerAdded writes UserId, current username/display name, first/last seen; refresh names without changing identity. Avatars use existing Roblox thumbnail paths with a fallback on failure.

Rows: avatar, username, copyable UserId, Warn 1/Warn 2/Warn 3… count (0 clearly identified), and plus action for an explicit warning/note reason and confirmation. Warned usernames are red with the textual count. Username opens one chronological warning history with reason, UTC timestamp, event ID and staff username/UserId. No automatic bans, edits, removals or escalation at any count; a report and warning are distinct record types.

Server-side search supports username, display name and exact UserId, matching the actual Members search semantics after targeted adapter inspection. Proposed page size 25, maximum 50, bounded query length and opaque validated cursor. Use canonical per-UserId records plus incrementally maintained name/display-name search indices and bounded paged directory indices, not an all-account client download or full DataStore scan per query. Name indices can lag or rename; recheck canonical matches and identify incomplete/unavailable search honestly. Exact-ID lookup remains direct. Arbitrary substring search is not a native DataStore query; if Members uses substring matching, choose an explicit bounded token/index strategy before claiming parity.

Warnings use server AdminBridge dispatch with a distinct moderation authorization policy, delegating storage to the moderation owner; do not loosen the existing GameTester gameplay gate. No new client admin-mutation remote or client-selected issuing identity. Per-target UpdateAsync atomically allocates monotonically increasing warning sequence, appends the event and its request receipt, and updates count. Repeated requests return the same event/count; simultaneous staff writes cannot overwrite each other. Bound page/record sizes; design rollover with recoverable pending writes and reconciliation before enabling long-running histories. Never assume separate event/index/count writes are transactional. Directory/read endpoints return only authorized pages, not private game resources. Retention/growth policy below determines storage page lifecycle.
