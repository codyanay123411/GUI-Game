# Decisions

Substantial architectural decisions belong in this file. Do not silently reverse them later. If a decision changes, record the new decision and why the previous one was replaced.

## Development workflow

- **Cursor Local Agent on This PC.** Local agent work runs on this machine, not a remote cloud agent, unless a later decision says otherwise.
- **Roblox Studio MCP.** Use Studio MCP for live DataModel work, GUI, inspection, Play/Local Server sessions, and output. Those sessions are **development verification / Director acceptance testing**, not the project’s **first real playtest** (see Product direction).
- **Script Sync.** Version-controlled Luau lives on disk and stays in sync with Studio through Script Sync. `.luau` files are the source of truth for scripts.
- **Empty Script Sync folders.** Script Sync does not create Studio folders that contain no `.luau` files. Reserved directories keep a `_Placeholder.luau` ModuleScript that returns `{}` solely so the folder appears in Studio. Delete that placeholder when the folder has real project files. Do not put gameplay in placeholders.
- **Git / GitHub.** Use Git for history and rollback. The project’s **private GitHub** repository (`origin`) is an active part of the development workflow.

## Product direction

- This project is a **GUI-first multiplayer feudal grand-strategy and political RPG** for Roblox. Play is interface-driven (2D political map), not a traditional explorable 3D world, unless directors later change that.
- **Match:** approximately **30 minutes**, approximately **50 players**, one shared political world. History is **fictional and player-created** each match. Not a historical timeline and not a clone of another game’s exact mechanics.
- **Subordination is gameplay, not elimination.** Being conquered or becoming a subject does not automatically remove a player from the match. Powerful subordinate play must remain viable.
- Previous **single-player-oriented** development assumptions are **superseded**. **Political Hierarchy V0.1 is accepted / complete** (human Lords, voluntary vassalage). **Territory / Map Foundation V0.1 is accepted / complete.** **Title Progression V0.1 is accepted / complete.** **Diplomacy V0.1 is accepted / complete.** **Warfare / Conquest V0.1 is IMPLEMENTED — DIRECTOR-VERIFIED — DIRECTOR-ACCEPTED** (V0.1 only; not a complete military simulation). **Economy / Resources V0.1 is IMPLEMENTED — NOT DIRECTOR-ACCEPTED.** Currently approved core play treats the human as their match ruler; do not implement aging, family simulation, generational succession, or natural character death. Further hierarchy features still require director authorization.
- Victory conditions remain **conceptual** (final victory math is deferred). The **first real published playtest** still requires a coherent match that can reach a conclusion with a determinable winner; how that winner is decided for that playtest is **not yet specified** (do not invent a victory formula here).
- **First real playtest (Director definition).** Studio Play Solo, Local Server synthetic clients, MCP sessions, isolated regressions, and Director acceptance checks are **development verification**, not the first real playtest. The first real playtest is a **published Roblox server**, Director + friends / actual human players joining normally, **one completed map**, GUI sufficiently polished and intentionally laid out, core backend systems implemented and integrated, a coherent playable match loop of about **30 minutes** from beginning through conclusion, with a winner that can actually be determined. Multiple maps are **not** required for that playtest. The build should feel like a playable game, not a stack of debug prototypes.
- **Terminology:** **territory** = land / province / map holding. **Title** = political rank/progression (Lord, Duke, King, Emperor). Do not interchange these terms.
- **Pre-playtest usability (locked, not current implementation).** Required before the first published playtest; do not implement unless the Director authorizes: (1) **player/map orientation** — a player must never have to guess where they are on the political map (restrained own-land identification, clear ruler↔realm-color relationship, TerritoryInfo holder/owner, convenient center-on / show-my-realm or equivalent, likely temporary own-realm emphasis; greater-realm viz should eventually distinguish personally held vs subject-held land while keeping the whole realm readable; **no keybind assigned yet**); (2) **admin copy/reuse UX** — when admin/debug UI shows identifiers an administrator may reuse (war IDs, request IDs, ruler IDs, territory IDs, etc.), provide convenient in-game copy/reuse when practical; command bar remains; do not build a polished admin dashboard now; (3) **player-relevant information** (implemented for Warfare GUI; standing for future systems); (4) coherent GUI layout and major-interaction clarity. Treat these as **required usability**, not optional decoration. Do not implement them while baseline systems are still being completed unless authorized.

## Political hierarchy (V0.1 — specified and implemented as a limited prototype)

- Foundational system. Nested ruler-to-ruler trees. Server-authoritative. Clients may request and display; the server validates.
- **V0.1 implementation:** `PoliticalHierarchyService` owns truth. Two Studio remotes: `HierarchyClientEvent` (intents) and `HierarchyServerEvent` (state/notices). Shared rank rule lives in `PoliticalRankRules` for display and server validation; the server always revalidates.
- **Normal play:** joining humans are Independent Lords. Higher landed ranks (Duke / King / Emperor) are established through Title Progression V0.1 when qualified; server debug/test fixtures remain available.
- **Voluntary vassalage (player-facing term: Vassalage, not Fealty):** offer → accept/decline; both must agree; requests expire after **30 seconds** (V0.1 tuning). Expired/stale/superseded requests cannot mutate hierarchy. After accept or decline, the server notifies **both** the initiator and the receiver.
- **Disconnect (temporary prototype):** leaving players have their runtime ruler removed; direct vassals become independent; descendant trees of remaining rulers stay intact. No AI replacement, reconnection, succession, or persistence. Territory / Map Foundation V0.1 listens to hierarchy `RulerRemoving` and sets that leaver’s **directly owned territory to Unclaimed**.
- **Ranks:** Lord → Duke → King → Emperor (four primary landed levels). This supersedes earlier Count-tier wording.
- **Normal start:** every participating player is an **Independent Lord** with **one** starting territory. No player Dukes/Kings/Emperors at match start.
- **Independence** is a status, not a rank. Rank and independence are separate.
- Distinguish **direct liege**, **direct vassals**, **indirect subjects**, independent rulers, top ruler, and greater-realm membership.
- **Voluntary vassalage** (both agree): allowed to equal or higher rank; **never** to lower rank. Equal-rank vassalage is allowed so blocs can form at Lord before higher titles exist.
- When a ruler’s liege changes (join or leave a greater realm), **existing subordinate trees stay attached**. Do not flatten internal hierarchy.
- Humans and NPCs may eventually share the same conceptual rules; detailed NPC political AI is unspecified.
- **No cycles.** Reject becoming subordinate to someone already in your subordinate tree.
- Title **establishment:** see **Title Progression V0.1** (accepted / complete). Sequential next-rank only. Vale test numbers are map-specific. Prestige is a threshold, **not spent**. Gold/Influence are not requirements. No auto-promotion. No auto-demotion. Title-loss remains unresolved.
- **Unresolved (do not invent):** title-loss; vassal obligations (Economy V0.1 has no automatic tax; tax formulas remain unspecified); independence methods; disconnect/reconnect; join-in-progress; title-scaling for maps other than Vale V0.1 test thresholds. Hierarchy-changing war outcomes (forced vassalage, independence) remain unspecified. **Warfare / Conquest V0.1** transfers territory on valid attacker victory only; it does not change liege/vassal links. Economy V0.1 does not steal Gold on conquest.

## Maps, title scaling, economy, monetization (checkpoint — Gold V0.1 now specified separately)

- Primary board: large interactive GUI political map. Multiple fictional maps; territory counts may differ; geography is stable per map and separate from political realm names. Map size and title scaling do **not** depend on human player count.
- `TitleRequirements = f(MapConfiguration)` — deterministic, configuration-driven. Greater-realm control counts. Do not hardcode universal X/Y/Z territory counts. **Vale Title Progression V0.1 test numbers** (Duke 2/100, King 5/250, Emperor 10/500) are locked for that prototype map only.
- Match resources reset each match: **Gold** (economic), **Prestige** (legitimacy), **Influence** (political leverage) — conceptually distinct. Do **not** introduce Credits as a Gold replacement.
- **Economy / Resources V0.1** is the **Gold foundation** (**IMPLEMENTED — NOT DIRECTOR-ACCEPTED**). Prestige remains Title V0.1 test Prestige. Influence remains deferred. See **Economy / Resources (V0.1)** below.
- Account-level persist: **Crowns** (premium/cosmetic working name; not competitive match power) and **Lifetime Support** (non-spendable statistic; spending Crowns does not reduce it).
- Prefer procedural/curated naming, not external generative AI. Default realm names on title establishment; custom names optional and must be filterable. Never block establishment for lack of a custom name.
- Simulation performance: store state; calculate on meaningful change; do not poll/recalculate unchanged political info every frame.

## Territory / Map Foundation (V0.1 — accepted / complete)

- Reusable interactive political world map. GUI-first. Renderer is **map-agnostic**: current `MapConfiguration`, not a hardcoded 16-province system. V0.1 happens to use one **16-territory** test map; 16 is not a universal future count.
- Maps are **hand-authored presets**, not per-match procedural worlds. Multiple future maps may differ in count, shape, names, adjacency, and layout. No required recommended-player-count metadata. AI filling gaps is future; **no AI in V0.1**.
- **Territory** = smallest ownable unit; not subdivided. Static map definition: ID, display name, polygon geometry, adjacent IDs. Match state: owner and political/realm relationship. Do not bake ownership into geometry.
- Visuals: stylized **irregular polygons** (not hexes); fictional geographic names belong to the land, not the ruler (examples only: Westmere, Northvale, Greyfen, Highmarch).
- Humans start with **one unique random** available territory assigned on join after the ruler exists. No fixed Player1/Player2 slots. Unused territories are **Unclaimed** (neutral gray, still selectable). No NPC rulers to occupy leftovers. Practical V0.1 capacity = 16 starting humans. **17th human / no free territory is unresolved — do not invent.**
- Disconnect (with existing hierarchy cleanup): leaver’s directly owned territory → Unclaimed. No AI, reconnect, or succession.
- Realm colors: automatic curated palette; players do not choose in V0.1. Greater-realm fill vs direct-owner secondary indicator. Ownership ≠ hierarchy membership. Do not change Political Hierarchy V0.1 to achieve this.
- Every territory selectable. Info panel: name, ID, owner, rank, independent/subject, greater realm/root. Unclaimed labeled Unclaimed. Territory / Map V0.1 itself has no economy/religion/buildings. No claim/conquer/trade/gift/purchase **as Territory / Map gameplay**. Economy V0.1 is a **separate** Gold system that **reads** ownership. Server-only debug ownership changes allowed for tests, not as gameplay. Player conquest of enemy-held **territory** is **Warfare / Conquest V0.1** (**IMPLEMENTED — DIRECTOR-VERIFIED — DIRECTOR-ACCEPTED**).
- Desktop: pan, wheel zoom, click select; bounded camera; initial view frames the test map. Touch/controller not required. **“Focus my realm” / player orientation is not Territory / Map V0.1** (accepted without it). It is **required before the first published playtest** (see Product direction); do not assign a key or implement it unless the Director authorizes it. Adjacency stored from day one. **Vale prototype (director-corrected):** immediate 4×4 neighbors include **edge or corner** (8-neighbor); two cells away is not adjacent. Other maps author their own lists. Territory / Map V0.1 does not declare wars; **Warfare / Conquest V0.1** queries adjacency and ownership.
- Server authoritative over ownership, assignment, and match map state. Client renders and displays. Calculate-on-change.
- **Implementation (2026-08-23):** `MapCatalog` / `ValePrototypeMap` (`vale_prototype_16`, 16 jittered quads, authored 8-neighbor adjacency). `TerritoryMapService` owns match ownership; clients request a snapshot via `TerritoryClientEvent` Ready / `TerritoryServerEvent` State (JSON). Renderer is ViewportFrame + WedgePart triangles (EditableImage blocked by Studio security). Fill = greater-realm color; inset rim = direct holder; selection is a separate inward gold ring (does not replace fill or holder color). `DebugSetOwner` is server-only. Client remotes do not mutate ownership. **Accepted / complete** after director two-client runtime testing (unique starts, Unclaimed remainder, pan/zoom, vassalage visualization, disconnect Unclaimed). Vale adjacency was later director-corrected from 4-connected to edge-or-corner immediate neighbors and that 8-neighbor graph is **director-verified**. Map V0.1 acceptance does **not** authorize warfare, claims, economy, AI, persistence, extra maps, or other deferred systems.

## Title Progression (V0.1 — accepted / complete)

- Sequential landed ranks only: Lord → Duke → King → Emperor. No skipping.
- Qualification uses **greater-realm** territory control (direct holdings of the ruler plus subordinate tree), derived from existing hierarchy + territory ownership. Do not duplicate hierarchy authority. Establishment does not consume land.
- Eligibility and establishment are separate. Manual player action. Server revalidates. Client display is informational. No auto-promotion.
- Vale prototype **test** thresholds (not universal): Duke 2 territories / 100 Prestige; King 5 / 250; Emperor 10 / 500. Lord has no establishment. `TitleRequirements = f(MapConfiguration)`.
- Prestige in V0.1 is **temporary server-side test Prestige**. Checked, **not spent**. No Prestige economy. No client Prestige mutation.
- Established titles are **not** auto-demoted if control later falls below the creation threshold. Title-loss systems remain unresolved — do not invent them.
- Rank is not the political realm’s custom name. V0.1 naming may use a simple default for UI; full naming/custom UI is deferred; lack of a custom name must never block establishment.
- Rank change does not automatically rewrite liege/vassal links or flatten trees. Do not invent hierarchy restructuring.
- Title system must not own or mutate map geometry/ownership. Hierarchy and map V0.1 stay accepted.
- **Implementation (2026-08-23):** `TitleRequirements` reads `MapConfiguration.titleRequirements` (Vale rows only). `TitleProgressionService` reads hierarchy + ownership, holds per-ruler test Prestige (default 0, not spent), recalculates eligibility on change, and grants the next rank via `PoliticalHierarchyService.SetTitleRank` after revalidation. Client `TitleProgressionController` shows current/next/control/Prestige/eligibility and fires `Establish` intent only. Remotes: `TitleClientEvent` (Ready / Establish) and `TitleServerEvent` (State / Notice). Server-only debug: `DebugSetPrestige` and `ServerScriptService.TitleProgressionDebug` attributes (Play Server `_G.__TitleProgressionV01` may be nil in the Command Bar VM; the attribute bridge is the supported live setter). Rank change does not alter liege/vassals/land. Incoming vassalage uses `VassalageOfferOverlay`. **Accepted / complete** after director Local Server + 2 Players testing (vassalage, 2-realm Duchy eligibility, server-side 100 test Prestige, on-screen Establish Duchy, both clients saw Duke, prestige not spent, map/hierarchy/territory regression pass). Acceptance does **not** authorize a real Prestige economy, title-loss, warfare, claims, AI, extra maps, or other deferred systems.

## Diplomacy (V0.1 — accepted / complete)

- External formal agreements **between independent greater realms**, conducted only by **root rulers**. Subjects cannot independently offer, accept, decline, or break those agreements. Vassal diplomatic autonomy is **not** V0.1.
- Exactly two types: **Alliance** and **Non-Aggression Pact**. They may coexist; neither auto-creates or auto-removes the other.
- V0.1 meaning is declarative Alliance/NAP state in Diplomacy. Diplomacy does not auto-join wars, auto-break NAP, or apply war penalties. **Warfare / Conquest V0.1** (implemented) **queries** that state: NAP **blocks** war declaration; Alliance does **not** auto-join.
- Server-authoritative. Clients send intents only. Server revalidates independence/root using **Political Hierarchy** truth; do not duplicate the hierarchy tree.
- Offer → pending (30s) → Accept / Decline / Expire. Only server Accept creates the agreement. Unordered duplicate pending/active of the **same** type is rejected; Alliance pending does not block NAP pending. No self-diplomacy. No rate limits.
- Either root may unilaterally break one agreement type without affecting the other. Both sides get feedback. No V0.1 penalty.
- **Locked:** losing independence **dissolves** that ruler’s external agreements and invalidates their pending external requests. Agreements do **not** transfer to the new liege.
- Disconnect: remove that ruler’s agreements and pending requests. No persistence, reconnect, AI, succession, or inheritance.
- No effect on map ownership/colors/geometry or on titles/Prestige/eligibility.
- **Implementation (2026-08-23):** `DiplomacyService` stores unordered-pair Alliance/NAP flags and 30s pending requests; remotes `DiplomacyClientEvent` / `DiplomacyServerEvent`; query `AreAllied` / `HasNonAggressionPact` via root ids. Client `DiplomacyController` + `DiplomacyPanel` (right column above Title) and `DiplomacyOfferOverlay` (priority Accept/Decline). Map input layering includes those surfaces. Prototype debug: `ServerScriptService.DiplomacyDebug.Invoke` (Play Command Bar `_G.__DiplomacyV01` may be nil). **Accepted / complete** after director Local Server multiplayer verification: human GUI offer → second-client overlay; Alliance Accept; NAP Accept; Alliance/NAP Decline; Alliance + NAP coexistence; independent Break; both clients updated after agreement changes; 30s pending expire; subject read-only diplomacy; loss of independence dissolves external diplomacy with no transfer to the new liege; disconnect of an independent ruler with active diplomacy removes that ruler and dissolves the survivor’s agreements; diplomacy remains rooted at the independent greater-realm ruler; no observed regression to hierarchy, territory/map, title progression, GUI layering, pan/zoom/select, or prototype theme/layout. Acceptance does **not** authorize deferred military systems, opinion, vassal diplomatic autonomy, or other deferred diplomacy.
- **Do not implement** opinion, vassal diplomatic autonomy, or other deferred diplomacy from this Diplomacy section.

## Warfare / Conquest (V0.1 — IMPLEMENTED — DIRECTOR-VERIFIED — DIRECTOR-ACCEPTED)

- Infrastructure testing only. Independent **root rulers** declare external wars. Subjects do not independently declare. Do not duplicate the hierarchy tree.
- Each war targets **one** enemy-controlled (not Unclaimed, not own-realm) territory that is MapConfiguration-adjacent to **any** holding in the attacking **greater realm** (Vale: immediate edge or corner neighbor; **8-neighbor lattice director-verified**).
- Declaration is immediate if the server validates. No Accept/Decline. Defender does not consent. Client intent `DeclareWar(territoryId)` only.
- **NAP** (Diplomacy truth) **blocks** declaration. Warfare does not auto-break NAP or apply penalties. **Alliance** does not auto-join.
- Multiple simultaneous wars allowed, including multiple wars on the **same** target. Duplicate **same attacker + same target** is rejected. Opposite-direction wars are ordinary separate objects.
- Resolution is **server-only debug** Attacker Victory / Defender Victory. Not player authority. Revalidate before transfer. Attacker victory: target → **direct ownership of the attacking root**. Defender victory: war ends, ownership unchanged.
- If the target has already left the **original defending greater realm**, competing wars are **stale**: terminate without transfer; do not retarget the new owner.
- Disconnect of a participating root, or that root’s loss of independence, **terminates** affected wars. No automatic victory, no liege inheritance of the war, no disconnect transfer.
- Consume Hierarchy, Territory ownership/adjacency, and Diplomacy queries. Title Progression may observe new control counts; warfare does not grant rank/Prestige.
- **Implementation (2026-08-23):** `WarfareService`; remotes `WarfareClientEvent` / `WarfareServerEvent`; shared `WarfareAdjacency`; Vale 8-neighbor `ValePrototypeMap`; `TerritoryInfo` Declare War + war status (territory-named / additional-war copy). Player GUI filters via `PlayerRelevantView` (local `rootRulerId`); that helper is **not** war authority. Debug: `ServerScriptService.WarfareDebug.Invoke` (`Declare` / `Resolve`) and `LastSnapshot`. Play Command Bar `_G.__WarfareV01` may be nil.
- **Director verification (accepted 2026-08-24):** pan/zoom/select; greater-realm and vassal-border declaration; non-adjacent and true non-neighbor rejection; subject cannot declare; NAP block + break restores eligibility; immediate declaration (no diplomacy prompt); multiple territorial wars between same roots; duplicate attacker+target rejection; additional-war presentation; diagonal/corner adjacency; **Attacker Victory PASS** (Greyfen `warId` `d34b9750-29ff-4c8a-bb22-f066c334f04b`); **Defender Victory PASS**; **competing same-target wars PASS**; **stale-war cleanup after first attacker capture PASS**; **loss of independence during an active war PASS** (war terminates; new liege does not inherit); **defender-root disconnect PASS**; **attacker-root disconnect PASS** (most recent: Player1 attacker vs Player3 defender, target frostfield; remaining client “War cancelled (left the match).”; ordinary Territory UI no active wars; no transfer); **no stale active war after disconnect PASS**; ordinary Warfare GUI player/realm-relevant **PASS**; admin InspectWars global **PASS**; AdminBridge ResolveWar uses `WarfareService.DebugResolveWar` **PASS**. Vale 8-neighbor correction is **director-verified**. Multiple simultaneous wars on the same territory remain allowed; do **not** add a one-war-per-territory restriction.
- **Accepted / complete for V0.1.** Not a complete military game. Future armies, battles, war score, peace, claims/casus belli if adopted, occupation/sieges if adopted, and presentation polish must **build on** this authority. Do not start those systems unless the Director authorizes them. Do not reopen Warfare acceptance for Economy. Conquest does not steal Gold (Economy V0.1).

## Economy / Resources (V0.1 — IMPLEMENTED — NOT DIRECTOR-ACCEPTED)

- Gold foundation only. Not the finished economy. **Not director-accepted.** Do not invent shops/buildings/armies as Gold sinks. Do not collapse Gold/Prestige/Influence. No Credits.
- **Start:** 150 Gold per ruler (prototype; not permanent finished balance).
- **Config:** per-territory `baseGoldIncome` (Gold/min) on `MapConfiguration`. Vale = 10. Economy translates to ticks via `EconomyPayout` (`goldPerMinute * 6 / 60` must be a whole number or Start errors).
- **Income:** global 6-second server tick; Vale +1 Gold/tick per directly owned baseline territory. **Recipient:** **direct owner**. Unclaimed pays **nobody**.
- **Conquest:** future income stream only; no treasury loot. **Subjecthood:** personal Gold unchanged; subject still receives their direct-owner income; liege gets no automatic share.
- **Disconnect/removal:** Gold state destroyed with the ruler; no redistribution. Polished wealth succession is **unresolved**.
- **Spend:** `TrySpend` / `AddGold` / `DebugSetGold`. No player-facing sink. Never negative; no debt; no partial spend.
- **Implementation (2026-08-24):** `EconomyService` after Hierarchy + Territory. Remotes `EconomyClientEvent` (Ready only) / `EconomyServerEvent` (per-player State). HUD `EconomyPanel`. AdminBridge `;inspectgold` `;setgold` `;addgold` `;spendgold`. `EconomyDebug.Invoke`. Bootstrap order: Hierarchy → Territory → Title → Diplomacy → Warfare → Economy → Admin.
- **Director-verified PASS (2026-08-24 Local Server; acceptance paused, not accepted):** multiplayer start 150 + shared global 6s clock; direct-owner 10 Gold/min and +1/+2/+3 per tick with 1/2/3 lands; conquest redirects future income without treasury steal (landless defeated ruler +0 and treasury stopped); subject keeps Gold and land income, liege gets no share; unclaimed pays nobody. **Next resume test:** `;spendgold` success vs overspend (zero deduction, never negative, no partial spend).
- **Tall vs wide:** **future direction**, not V0.1.
- **Must not:** Civ strategic resources, food/wood/stone/iron, trade goods, population/manpower, tax-law, markets, debt, buildings, development, realm treasury, inheritance, military upkeep.

## Delegated greater-realm authority (future architecture — not implemented)

- **Effective authority** = rank defaults + individual overrides. Realm-specific policy. Root remains ultimate authority. Subject status alone grants nothing.
- Rank defaults (example: Emperor configures Kings/Dukes/Lords) are **not** universal hardcoded “all Dukes can X.” Individual overrides can grant or restrict a particular subject.
- Delegation = act **on behalf of** the greater realm. Does not create independence, another root, hierarchy changes, automatic territory transfer, or automatic personal-Gold transfer.
- Permissions = gameplay capabilities, not GUI buttons. Catalog **unresolved**. Do not retrofit into accepted V0.1 systems. Future systems add hooks after their own APIs exist.
- Economy V0.1 Gold is personal. Cross-ruler economic powers (realm treasury, tax, spending authority) require explicit future design.

## Source layout

- **Server** lives under `ServerScriptService`. `Services/` is reserved for authoritative server-side systems. `Bootstrap.server.luau` is a thin orchestrator only.
- **Client** lives under root-level `StarterPlayerScripts/` on disk, which Script Sync maps to `StarterPlayer.StarterPlayerScripts` in Studio. Do not use a nested `StarterPlayer/StarterPlayerScripts/` disk path. `Controllers/` is reserved for client behavior and GUI control. `Bootstrap.local.luau` is a thin LocalScript orchestrator only. Do not use `Bootstrap.client.luau` in this folder (Client RunContext Scripts run twice under `StarterPlayerScripts`).
- **Shared** lives under `ReplicatedStorage/Shared` (`Config/`, `Types/`, `Util/`). Shared modules must be safe for both sides and must not grant the client authority.
- **Remotes** live under `ReplicatedStorage/Remotes`. That folder is reserved for RemoteEvents and RemoteFunctions. Remote instances are created in Studio, not as Luau files.
- **GUI instances are not source-controlled as files.** They are created and edited through Roblox Studio MCP / Studio. Controllers drive GUI behavior; Services own authoritative state and validation. New GUI must integrate into one coherent prototype interface (central map when present; supporting panels/overlays; Play-mode verification). Not a license for an unsolicited full UI redesign. **Critical temporary actions** (incoming Vassalage Accept/Decline) must not depend on leftover space inside a permanently visible info panel; they use a map-centered overlay. Result toasts remain non-interactive outcome notices. **Prototype geometry:** primary panels (`Main`, `TitlePanel`, `MapStage`, `TerritoryInfo`) keep stable assigned regions; rank/eligibility/tree updates change content inside those regions, not panel Size/Position. Lists scroll in place. Future player-driven open/collapse is separate. **Prototype theme:** `ReplicatedStorage.Shared.Util.PrototypeGuiTheme` is the shared visual language for current panels/overlay/toast/buttons. Overlay stays more prominent; toast stays transient. Not final art.
- **Future UI shell (specified, not implemented).** The map should eventually fill the usable main canvas. Hierarchy, titles, diplomacy, economy, religion, and similar systems should open as contextual panels/overlays, not as permanently stacked chrome. Activation will use on-screen navigation and/or keybinds; **keys are not assigned**; navigation/bindings must be centralized. Major-panel open state should replace or coexist deliberately. Priority action overlays stay above whatever panel is open. Toasts stay separate. Functional clarity first. Do not implement this shell or add keybinds from this checkpoint.
- **Input layering / click-through (standing).** A higher-priority visible GUI that occupies the pointer must consume it; the map must not also pan, zoom, or select. Block input to the **bounds** of that GUI, not the whole screen by default. Do not rely on ZIndex alone. **Map implementation:** `TerritoryMapController` uses `GetGuiObjectsAtPosition` on pointer events for `VassalageOfferOverlay`, `DiplomacyOfferOverlay`, `TitlePanel`, `Main`, `TerritoryInfo`, `DiplomacyPanel`, `AdminInspectPanel`, and `EconomyPanel`, plus visible Kohl command-bar/dashboard chrome (`FluxUILayer*` CommandBar/Window/Dialog/K buttons). ResultToast is not a blocking layer. Mouse wheel over the map is allowed even when Roblox sets `gameProcessed` because `MapStage` is Active; that flag is not treated as higher-GUI blocking.
- **The client is never trusted** for authoritative game decisions.
- **Player-relevant information (standing).** Player-facing UI must use player/realm-relevant views of authoritative server state. Global server state is not automatically player-visible. Admin/debug inspection is exempt. Systems that intentionally expose global/public information must explicitly define that visibility. Default new-system question: public / local-realm / admin-only. Warfare ordinary GUI: local greater-realm wars only (`PlayerRelevantView`). `;inspectwars` stays global. Economy V0.1 ordinary UI: the local ruler’s Gold / income / payout countdown only.
- Avoid monolithic scripts. Do not introduce frameworks or external dependencies unless a later decision records that change. **Kohl's Admin** (when installed) is an exception as the chosen command UI; it must not own game state.
